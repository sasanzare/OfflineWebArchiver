# Acceptance Matrix

**Document status:** Proposed baseline  
**Owner:** QA Lead  
**Last updated:** 2026-08-07

This matrix is the authoritative inventory of product acceptance criteria.
Requirements are defined in [Project Scope](PROJECT_SCOPE.md); phases are defined
in the [Phase Plan](../project/PHASE_PLAN.md); fixtures are defined in the
[Test Fixture Strategy](../testing/TEST_FIXTURE_STRATEGY.md). Results cannot be
changed to `passed` without the named evidence.

## Vocabulary and rules

- **Status:** `defined`, `blocked`, `needs-decision`, `ready-for-test`, `passed`,
  `failed`, or `not-applicable`.
- **Priority:** Critical, High, Medium, or Low.
- `P<n>` means phase number. Implementation and validation phases are plans, not
  claims of completion.
- Preconditions that require an approval use the versioned Project measurement
  snapshot. Any unavailable business/platform input is also tracked in
  [Open Decisions](../project/OPEN_DECISIONS.md).
- Automated assertions must use deterministic fixtures; target-site checks use
  redacted evidence and the authorized acceptance plan.

## Status governance

- Phase 1 criteria are `defined` when their behavior and evidence are measurable.
  `needs-decision` means the test is measurable but an external matrix, threshold,
  owner, or target input is unresolved.
- `ready-for-test` requires implemented code, reviewed test data, and satisfied
  preconditions. `passed` requires retained evidence and reviewer sign-off.
- A later phase may add criteria but must not weaken or silently renumber these.
  Superseded criteria remain in history with a replacement reference.
