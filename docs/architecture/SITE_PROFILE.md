# Site Profile

Site Profile schema `1` is the portable, strict, secret-free policy for one Project. `profile/config.json` is the configuration authority; SQLite schema `3` is the immutable revision and integrity ledger. The normalized Profile `baseUrl` is also copied to `project.json` as `source.baseUrl`; a mismatch between these values, the file SHA-256, active profile revision, Project ID, or database pointer fails closed.

Each profile stores stable Profile, Project, and Revision UUIDs; sequence; UTC timestamps; Base URL; seeds; authorization reference/status; domain/path/query/fragment policies; redirect/canonical/network policy; and bounded depth/page/redirect/batch limits. The Base URL is credential-free HTTP(S), uses the canonical ASCII host and non-default port, retains path/trailing-slash semantics, drops query/fragment, must pass the Profile's own scope rules, and is the fallback for relative resolution. Unknown fields, duplicate rule IDs, conflicting domain rules, invalid timestamps, credentials in seeds, unsafe schemes, and oversized collections are rejected.

Profile creation makes Project format `1.1.0`, enables `features.scopePolicy`, and advances the existing Project revision. Updates require the expected revision ID; normalized drafts with no semantic change fail as `PROFILE_NO_CHANGES` without advancing any revision. Real changes append immutable `project_revisions`, `site_profile_revisions`, and `scope_rules` rows, atomically replace the JSON and manifest while holding the Project lock, and compensate on failure. Injected ordinary failures restore both files and roll back SQLite. Cross-file/SQLite process-crash atomicity is not physically possible; startup validation detects the bounded commit window and never silently chooses a side.

Format `1.0.0` Projects remain readable and migrate forward. A profile is optional until explicitly created. Profiles never contain credentials, cookies, tokens, local host paths, or fetched data.
